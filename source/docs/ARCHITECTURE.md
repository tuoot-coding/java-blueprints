# Java Blueprints - архитектурные решения MVP

## Источник требований

AXENIX, кейс "Визуальная среда программирования - Java Blueprints", PDF на 12 страниц. Полный внешний технический документ с перечнем Java-конструкций в переданных материалах отсутствует.

## Цель продукта

Загрузка Java -> грамматический разбор -> структурная модель -> граф метода -> управляемое редактирование -> генерация обновленного Java -> компиляция и проверка поведения на фиксированном наборе тестов -> экспорт.

## Принятый стек

- Frontend: Next.js + TypeScript + Tailwind CSS + React Flow + Monaco Editor.
- Backend: Python + FastAPI + Pydantic v2 + tree-sitter-java + SQLite.
- Выполнение Java: изолированные одноразовые Docker-контейнеры на JDK 21, без сети и с лимитами ресурсов.
- Локальная разработка: Node.js LTS, Python 3.12+, Docker.
- Тестирование: pytest, Ruff, TypeScript strict, Vitest, Playwright для одного сквозного сценария.

## Разделение ответственности

- Frontend отвечает за интерфейс, хранение черновиков и layout графа. Исходную Java-семантику не определяет.
- Backend отвечает за истинную Java-ревизию, парсинг, модель графа, валидацию изменений, диагностику и регрессионную проверку.
- Граница между слоями - документированное и версионированное REST API `/api/v1`.

## Источники истины

- Канонический артефакт - текст Java-исходника конкретной ревизии.
- AST и CFG производные структуры.
- Позиции исходника исходно учитываются в байтах UTF-8; редактор требует корректной конвертации в UTF-16.
- Layout и раскрытость графа - только UI-состояние.
- Каждая модификация проверяет ожидаемую ревизию, применяет валидируемое изменение, повторно парсит и сохраняет новую ревизию.

## Уровни визуализации

1. Дерево проекта: файлы, классы, интерфейсы, методы.
2. Граф выбранного метода: реальный поток управления с разветвлениями и циклами.
3. Инспектор конкретного AST-узла: привязка к диапазону исходного текста и допустимым операциям.

Просто перетаскивать графовые узлы можно для раскладки. Смысловая правка требует поддержанной операции изменения исходника. Незнакомые Java-конструкции остаются в тексте и отмечаются ограничением.

## Базовый контракт API

- `POST /api/v1/projects` - загрузка исходников.
- `GET /api/v1/projects/{project_id}` - состояние проекта.
- `GET /api/v1/projects/{project_id}/outline` - структура классов и методов.
- `GET /api/v1/projects/{project_id}/graph?method_id=...` - CFG метода.
- `GET /api/v1/projects/{project_id}/diagnostics` - диагностика.
- `PUT /api/v1/projects/{project_id}/source` - сохранение исходника с expected_revision.
- `POST /api/v1/projects/{project_id}/edits/preview` - предварительная проверка трансформации и diff.
- `POST /api/v1/projects/{project_id}/edits/commit` - подтверждение правки.
- `POST /api/v1/projects/{project_id}/test-cases` - добавление тестового входа.
- `POST /api/v1/projects/{project_id}/runs` - запуск сборки/тестирования.
- `GET /api/v1/runs/{run_id}` - статус выполнения и результаты.
- `POST /api/v1/projects/{project_id}/compare` - сравнение исходной и новой ревизии.
- `GET /api/v1/projects/{project_id}/export` - экспорт исходников.

Контракт является проектным предложением, а не опубликованным API организаторов. Его следует зафиксировать OpenAPI до параллельной реализации.

## Gate качества

- Без изменений Java-текст после round-trip не отличается от загруженного.
- Для каждого поддержанного CFG-перехода есть тест.
- Неуспех парсинга или компиляции не превращается в успешный ответ.
- Тест сравнения использует сохраненный baseline, совпадающие входы и определенное правило сопоставления stdout/stderr/exit_code.
- Статус `passed` запрещен без фактического запуска.
- Docker недоступен - выполнение заблокировано, host-fallback запрещен.

## Приоритеты

P0: импорты/парсинг/outline/граф метода/редактор/обратная сборка/контроль ревизий/запуск и сравнение/демо.
P1: диагностика сложности, безопасные трансформации, подсветка AST-кода, экспорт.
P2: улучшенный автоматический анализ, декомпозиция, бонусные конструкции Java, расширенные визуальные эффекты.

## Риски

- tree-sitter строит синтаксическое дерево, но не делает полноценного разрешения типов и семантического анализа.
- Точность CFG для исключений и `finally` требует отдельного проектирования и тестов.
- Оценки Big O являются эвристиками, а не математическим доказательством.
- Автоматическая оптимизация может изменить поведение даже при успешной компиляции.
- Набор тестовых входов должен быть задан или сформирован явно; произвольный `main` не имеет гарантированно известного набора корректных stdin.
- Docker как песочница снижает риск, но не гарантирует абсолютную безопасность на публичном многопользовательском сервере.
